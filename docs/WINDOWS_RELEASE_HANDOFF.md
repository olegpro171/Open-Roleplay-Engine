# Windows handoff for Task 2 — PowerShell and double-click launcher

Status: batch/PowerShell implementation and automated Windows x64 validation are recorded in [WINDOWS_RELEASE_VERIFICATION.md](WINDOWS_RELEASE_VERIFICATION.md); remaining manual/external gates are explicit there. The assignment below is retained as the acceptance contract. This is a platform subtask of [RELEASE_IMPLEMENTATION_BRIEF.md](RELEASE_IMPLEMENTATION_BRIEF.md), not a third product feature.

Accepted Windows delivery refinement: use a double-clickable `start-app.bat` entry and Windows PowerShell 5.1 scripts, with ordinary bundled `node.exe` as the application runtime. A custom `ORE.exe` is not required for the private beta. This supersedes the earlier executable requirement in CONCEPTS.md, IMPLEMENTATION.md and RELEASE_IMPLEMENTATION_BRIEF.md; do not introduce an executable packaging toolchain to satisfy that older wording. Update those documents consistently when implementing Windows delivery.

Latest startup decision (2026-10-20): users start a platform-specific entry script which checks latest remote `main`, builds only when needed, then launches. Windows must provide a native `.bat`/PowerShell entry for this workflow, with the private runtime and application as supporting files. Separate manual build and launch are no longer the normal flow. Daily source startup must use a fixed `ore-portable/` directory inside its repository, with no destination argument, matching the Mac/Linux entries. The Mac/Linux policy is implemented by `scripts/release/update-and-start.sh`; do not require Bash on Windows. Reuse its committed-main comparison, private managed checkout, fast-forward-only updates, preserved user edits/data/languages, update lock, visible offline/build-failure fallback and explicit no-check recovery mode. Use Git authentication without embedding credentials or installing global toolchains. Test the same first-start, unchanged, update, failure, cancellation and recovery cases natively.

## Prompt for the Windows Codex agent

Implement and validate Windows delivery of ORE as `start-app.bat`, PowerShell scripts and a supporting folder containing the private Node runtime and built application. Read AGENTS.md and the release brief first. Start from a clean current main commit containing the shared startup/recovery fixes, unless the user supplies a specific commit. Record the full base SHA in your report. Inspect the current filesystem/launcher contract and reuse it; do not invent a competing package layout. Work on a `codex/` branch and preserve existing changes. Do not publish, merge or upload artifacts without user instruction.

The user explicitly accepts supporting files. Retain the current local Fastify server and browser UI. Bundle the supported Node LTS runtime, built app/UI, migrations, production packages and required native libraries. The end user should not need Node, npm, Python, Visual Studio build tools, global SQLite or image libraries. Build-machine tools are distinct from runtime prerequisites; explain any additional packaging tool before installing it and keep it app/project-scoped when possible.

Start with a declared Windows version/CPU target, normally Windows x64 if that matches the supplied machine. Do not claim ARM64 support unless separately built and tested. Use a verified official runtime and the repository lockfile; build/install the native dependencies for Windows rather than copying macOS node_modules. Validate whether pinned dependencies require redistributable system components and report actual prerequisites instead of assuming they are absent.

Keep `start-app.bat` small: locate the PowerShell entry relative to the batch file, invoke `powershell.exe` with `-NoProfile -File` and correctly quoted paths, preserve its exit code, and keep failures readable after a double click. Do not change the caller's directory before resolving relative database overrides. Put update/build orchestration in PowerShell; reuse shared Node modules for staging, readiness, database identities and recovery where practical. Target Windows PowerShell 5.1 without requiring PowerShell 7, Bash or administrator elevation. Check native command exit codes explicitly; PowerShell error preferences alone do not establish that Git/npm/Node succeeded. Test spaces, Unicode and shell metacharacters in paths, and ensure pointer/JSON text encoding matches the shared readers (PowerShell 5.1 output defaults must not introduce UTF-16 or an unexpected BOM).

If a script execution-policy override is needed, scope it to the launched PowerShell process. Never change persistent user/machine execution policy, profiles or security settings. Respect organization-managed policy and report blocks clearly. See [Microsoft's execution-policy documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1). Preserve normal Windows trust prompts; do not claim the scripts are signed.

Use existing Git and its configured repository authentication as the initial update prerequisite. Detect missing Git or unavailable credentials explicitly: first installation needs an actionable error; an existing usable installation should remain launchable offline. Do not silently install Git, credential helpers or global toolchains. If an app-local Git distribution is needed, propose its concrete dependency, download verification and maintenance cost before adding it.

The launcher starts ORE using its private runtime, provides useful errors and a stop path, and opens/displays the correct localhost URL only when ready. Its working directory must not matter. Ensure image-child processes and lore workers run correctly and do not recursively invoke the launcher. Keep all bundled files and caches in declared ORE-owned locations; preserve the data directory across updates.

Use synthetic data and local mock providers. Do not use saved user keys or private chats. Validate both the developer suite and the packaged output; source tests alone cannot prove the installed application includes its runtime resources.

## Required Windows checks

1. Build from the exact release candidate commit; record Node/npm, CPU, Windows and native package versions. Run typecheck/build, Vitest and Playwright using the supported environment, investigating failures rather than skipping them to produce a package.
2. Launch the package in a clean Windows account/environment without a globally available Node/npm or compiler toolchain. Double-click the `.bat` entry in Explorer and invoke it from a terminal in another directory; include spaces, non-ASCII characters and shell metacharacters in the installation path. Verify Windows PowerShell 5.1, missing Git/authentication, script-policy failures, meaningful exit codes and readable errors. Repeat startup offline with the local mock provider.
3. Exercise login, libraries, PNG/JPEG/WebP import/crop, chat generation/variants, reasoning, lore regex, compaction/repair and saved-request inspection. These cover SQLite, sharp/libvips, child processes, workers, tokenizer and frontend assets.
4. Stop/restart and confirm saved content. Test Ctrl+C, closing the console window, occupied port, repeated launch, second database owner, abrupt termination and recovery. Confirm that cancellation during download/build cannot leave background work activating a release after the launcher exits; verify lock cleanup or actionable stale-lock recovery. No automatic provider retries or orphaned app workers. Do not weaken authentication, origin checks, loopback defaults or LAN TLS requirements.
5. Upgrade a populated synthetic installation from the supported previous version. Test failed downloads/checksums/builds, a build that succeeds but whose server cannot start, and documented recovery after migration. Test unchanged main without rebuilding, offline startup, concurrent updates and preservation of a dirty managed checkout. Move/rename a populated repository and verify its local database follows; a missing established external database must fail without creating a new file. Preserve data, runtime language packs and configured paths. An old version must refuse an unsupported newer database.
6. Round-trip a synthetic Mac/Linux-produced backup on Windows and a Windows-produced backup on the other available platform. Verify images, credentials (without printing them), histories, memory, overlap replacement and restart. Report cross-platform checks still pending if no second artifact/environment is available.
7. Inspect package contents and filesystem/environment changes: no user database, secret, development path or global Node installation; no persistent PATH, shell-profile or registry startup changes. Verify notices/checksums and cleanup of temporary files. Record script/download trust prompts and any runtime warnings honestly without claiming code signing was performed.

## Deliverables

- Committed source/scripts needed to reproduce the Windows package, integrated with the shared release workflow.
- A local package directory/archive containing a double-clickable `start-app.bat`, its PowerShell entry and support files, with manifest/checksums and short instructions. Keep build artifacts out of source Git unless repository policy explicitly requires otherwise.
- A report listing exact commit, build commands, environment, checks passed/failed/blocked, artifact path/size/checksums, runtime prerequisites and any signing limitation.
- Focused upstream changes for genuine portability issues, with regression coverage. Coordinate changes to shared startup/storage code; do not work around a Windows failure by relaxing integrity, security or lifecycle checks.

Windows delivery is not complete merely because the batch entry starts: the packaged application's native dependencies, workers, persistence and recovery must actually run on Windows.
