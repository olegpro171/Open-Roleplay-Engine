# Windows handoff for Task 2 — ORE.exe and supporting folder

Status: ready as an assignment template; run on the user's Windows machine after the shared release/runtime contract is implemented. This is a platform subtask of [RELEASE_IMPLEMENTATION_BRIEF.md](RELEASE_IMPLEMENTATION_BRIEF.md), not a third product feature.

Latest startup decision (2026-10-20): users start a platform-specific entry script which checks latest remote `main`, builds only when needed, then launches. Windows must provide a native `.cmd`/PowerShell entry for this workflow, with the executable/runtime as supporting implementation. Separate manual build and launch are no longer the normal flow. Daily source startup must use a fixed `ore-portable/` directory inside its repository, with no destination argument, matching the Mac/Linux entries. The Mac/Linux policy is implemented by `scripts/release/update-and-start.sh`; do not require Bash on Windows. Reuse its committed-main comparison, private managed checkout, fast-forward-only updates, preserved user edits/data/languages, update lock, visible offline/build-failure fallback and explicit no-check recovery mode. Use Git authentication without embedding credentials or installing global toolchains. Test the same first-start, unchanged, update, failure, cancellation and recovery cases natively.

## Prompt for the Windows Codex agent

Implement and validate Windows delivery of ORE as `ORE.exe` plus its supporting folder. Read AGENTS.md and the release brief first. Use the exact shared-work commit supplied by the user/coordinating agent; record it in your report. If that commit or filesystem/launcher contract is not available, inspect the branch and prepare Windows tooling observations, but do not invent a competing package layout. Work on a `codex/` branch and preserve existing changes. Do not publish, merge or upload artifacts without user instruction.

The user explicitly accepts supporting files. Retain the current local Fastify server and browser UI. Bundle the supported Node LTS runtime, built app/UI, migrations, production packages and required native libraries. The end user should not need Node, npm, Python, Visual Studio build tools, global SQLite or image libraries. Build-machine tools are distinct from runtime prerequisites; explain any additional packaging tool before installing it and keep it app/project-scoped when possible.

Start with a declared Windows version/CPU target, normally Windows x64 if that matches the supplied machine. Do not claim ARM64 support unless separately built and tested. Use a verified official runtime and the repository lockfile; build/install the native dependencies for Windows rather than copying macOS node_modules. Validate whether pinned dependencies require redistributable system components and report actual prerequisites instead of assuming they are absent.

Produce a genuine executable entry point, not a batch file renamed `.exe`. Select the smallest approach that meets the existing contract; no new desktop UI framework is required. The executable starts ORE using its own runtime, provides useful errors and a stop path, and opens/displays the correct localhost URL only when ready. The working directory must not matter. Ensure image-child processes and lore workers run correctly and do not recursively invoke the launcher. Keep all bundled files and caches in declared ORE-owned locations; preserve the data directory across updates.

Use synthetic data and local mock providers. Do not use saved user keys or private chats. Validate both the developer suite and the packaged output; source tests alone cannot prove the executable includes its runtime resources.

## Required Windows checks

1. Build from the exact release candidate commit; record Node/npm, CPU, Windows and native package versions. Run typecheck/build, Vitest and Playwright using the supported environment, investigating failures rather than skipping them to produce a binary.
2. Launch the package in a clean Windows account/environment without a globally available Node/npm or compiler toolchain. Test from Explorer and from a terminal in another directory; include spaces and non-ASCII characters in the installation path. Repeat startup offline with the local mock provider.
3. Exercise login, libraries, PNG/JPEG/WebP import/crop, chat generation/variants, reasoning, lore regex, compaction/repair and saved-request inspection. These cover SQLite, sharp/libvips, child processes, workers, tokenizer and frontend assets.
4. Stop/restart and confirm saved content. Test occupied port, repeated launch, second database owner, abrupt termination and recovery. No automatic provider retries or orphaned app workers. Do not weaken authentication, origin checks, loopback defaults or LAN TLS requirements.
5. Upgrade a populated synthetic installation from the supported previous version. Test a failed staged update and documented recovery after migration. Preserve data, runtime language packs and configured paths. An old version must refuse an unsupported newer database.
6. Once Task 1 exists, round-trip a synthetic Mac/Linux-produced backup on Windows and a Windows-produced backup on the other available platform. Verify images, credentials (without printing them), histories, memory, overlap replacement and restart. Report cross-platform checks still pending if no second artifact/environment is available.
7. Inspect package contents and filesystem/environment changes: no user database, secret, development path or global Node installation; no persistent PATH, shell-profile or registry startup changes. Verify notices/checksums and cleanup of temporary files. Record unsigned-executable prompts honestly without claiming code signing was performed.

## Deliverables

- Committed source/scripts needed to reproduce the Windows package, integrated with the shared release workflow.
- A local package directory/archive containing `ORE.exe` and support files, with manifest/checksums and short instructions. Keep build artifacts out of source Git unless repository policy explicitly requires otherwise.
- A report listing exact commit, build commands, environment, checks passed/failed/blocked, artifact path/size/checksums, runtime prerequisites and any signing limitation.
- Focused upstream changes for genuine portability issues, with regression coverage. Coordinate changes to shared startup/storage code; do not work around a Windows failure by relaxing integrity, security or lifecycle checks.

Windows delivery is not complete merely because an executable is produced: the packaged application's native dependencies, workers, persistence and recovery must actually run on Windows.
