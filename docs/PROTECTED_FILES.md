# Protected portable files

ORE protects downloaded backups with standard password-derived encryption. The optional password may be empty. A nonempty password must be supplied exactly on import; it is neither embedded in the file nor recoverable by ORE. Password strength still matters against offline guessing. An empty password only deters scanners that look for directly readable API keys. An ORE-aware tool can open empty-password files automatically; targeted extraction need not remain manual.

Protection applies to the entire portable snapshot, including credentials, story text and metadata, and to exported Connection profiles. It does not change the live database, local schema-upgrade recovery snapshots, HTTP LAN transport, or ordinary character/persona/preset exports. Connection keys are excluded from profiles unless explicitly included; the wrapper authenticates the content kind separately from backups.

## Workflow and transport

Settings → Data backup → Save... opens a dialog with optional password and confirmation fields visible immediately. Keep it separately from the downloaded `ORE-backup-<UTC timestamp>.orebackup` file. Under Import backup, select the file first, then enter the same password in the dialog and choose Import to inspect it. Failed attempts show errors inside the dialog and preserve its fields and selected file for explicit retry. Successful creation/inspection closes the dialog. Cancelling the dialog or closing Settings discards these transient values. No password is stored in localStorage, command receipts, request history or the artifact.

Authenticated, same-origin POST `/api/data/backup` accepts `{ "password": "…" }`. With `Accept: application/json`, it returns a prepared download link and filename; the browser follows that normal HTTP link instead of creating a Blob URL. The subsequent authenticated GET `/api/downloads/:token` sends the completed encrypted file with an explicit content length and attachment filename. This removes dependence on Blob URL lifetime, but does not eliminate the native macOS Safari finalization delay reproduced independently of ORE; see [download diagnostics](DOWNLOAD_DIAGNOSTICS.md). Direct POST callers without that Accept header still receive the binary file. Passwords never enter URLs. Binary POST `/api/data/stages` carries an optional `X-ORE-File-Password` header containing canonical base64 of the exact UTF-8 password. An absent/empty header means an empty password. Base64 only transports the header; it provides no additional secrecy. Existing application authentication, origin checks and transport policy still apply. Application request logging remains disabled.

Passwords are limited to 256 UTF-16 code units, matching the input and shared validator. There is no trimming, normalization or minimum length. The receiving installation does not need the sender's owner password or other local settings. After successful opening, the existing shipped-schema/content validation, paginated inspection, explicit import confirmation and transactional recovery apply. Existing plaintext SQLite backups remain accepted. Older ORE builds cannot read the new wrapper.

## Version 1 wire format

All lengths are bytes. No JSON, compression or executable metadata is outside the ciphertext.

| Offset | Length | Value |
| --- | --- | --- |
| 0 | 8 | ASCII `OREENC\r\n` |
| 8 | 1 | Wrapper version: 1 |
| 9 | 1 | Content kind: 1 for a backup, 2 for a Connection profile |
| 10 | 16 | Cryptographically random scrypt salt |
| 26 | 12 | Cryptographically random AES-GCM nonce |
| 38 | Payload length | AES-256-GCM ciphertext |
| End − 16 | 16 | GCM authentication tag |

Derive a 32-byte key using Node's scrypt implementation with the exact UTF-8 password, the stored salt, `N = 32768`, `r = 8`, `p = 1` and a 64 MiB working-memory ceiling. These are fixed version-1 parameters; uploaded files cannot request different work factors. Use AES-256-GCM with the 38-byte header as additional authenticated data and an explicit 16-byte tag. Each export generates fresh salt and nonce, even with a blank or repeated password. Future incompatible parameters require a new wrapper version; preserve version-1 reading.

The wrapper adds exactly 54 bytes. Backup plaintext remains bounded to 128 MiB; the HTTP/browser file bound allows those additional bytes. The wrapper version is independent of the inner portable format and SQLite schema version. Unsupported versions/kinds, malformed structure and oversized payloads fail before key derivation; incorrect passwords and failed authentication fail before any bytes reach SQLite. The authentication tag detects damage but does not establish a file's publisher. Imported content remains untrusted and must pass the ordinary validation.

## Connection profiles

Libraries → Connections offers **Export...** on each saved profile and **Import Connection...** in the toolbar. Export asks for an optional password and an unchecked **Include API key** option; checking it shows the credential-sharing warning. Save downloads `<name>.oreconnection`. Selecting an import file opens a password dialog; incorrect passwords preserve the selected file and fields for explicit retry. Cancel discards transient values. Pending submission prevents duplicate requests and dismissal. Imported profiles receive new identities and local dates without changing existing Connections, defaults or chat selections.

The inner UTF-8 JSON is `{ "format": "ore-connection", "version": 1, "connection": { … }, "apiKey": "…" }`, with `apiKey` omitted unless explicitly included. Settings and keys pass existing Connection validation; extra fields, including uploaded identities/revisions, are rejected. Plain JSON profiles are unsupported. Inner plaintext is bounded to 128 KiB, with a 54-byte wrapper allowance. Export and import share the backup encryption parameters, exact password behavior and two-operation derivation limit. Small profiles use buffers instead of temporary plaintext files; plaintext buffers are cleared after use.

Authenticated same-origin POST `/api/library/connections/:id/export` accepts `{ "password": "…", "includeApiKey": false }`, with both fields optional. Like backup export, `Accept: application/json` prepares a normal HTTP download; other callers receive the encrypted bytes directly. POST `/api/library/connections/import` accepts `{ "revision": 0, "password": "…", "base64": "…" }`; bounded canonical base64 transports the encrypted bytes in JSON. Passwords never enter URLs or persisted commands. Successful import creates the profile/key in the existing short library transaction after decryption and validation, rechecking the captured revision and idle state. Failed writes roll back the whole profile. Retrying a successful command with its old revision fails without creating a duplicate. An uncertain acknowledgement requires inspecting Connections before starting another import. Connection and backup kinds cannot be opened interchangeably. No schema migration is needed.

## Ownership and recovery

`src/shared/protected-files.ts` defines browser-safe bounds and format constants. `src/server/protected-files.ts` owns password transport validation, asynchronous scrypt, encryption/decryption and a process-wide bound of two simultaneous operations. Derived key buffers are cleared on every exit. No new dependency is required. Busy operations return an actionable error and require explicit retry.

Backup export first creates and sanitizes the existing private consistent snapshot, then streams it into a separate private encrypted file. Downloads receive only completed ciphertext. Successful encryption removes the temporary plaintext snapshot; direct download close or failure cleans its download directory. Encryption failures remove partial output and never fall back to a plaintext download. These are private temporary files, not a claim of physical secure erasure.

`src/server/downloads.ts` owns at most four pending prepared downloads. It retains only encrypted Connection buffers or completed private encrypted backup files, plus filename, length, expiry and a hash identifying the requesting session. A random 256-bit URL token also requires that same authenticated session; another session cannot use it. Prepared downloads expire after five minutes, with cleanup every 30 seconds and on access/shutdown. A completed GET consumes the link and releases its data; HEAD does not consume it. An interrupted transfer remains retryable within its expiry. Existing readers may finish before expired files are removed. No password, API key plaintext or persistent ticket record is retained. A server restart invalidates links; export again. `src/web/downloads.ts` validates the local download URL and filename and starts a normal HTTP attachment download without a Blob URL or revocation timer. The interface reports that the browser handles completion, rather than claiming the file has reached disk.

Import buffers at most the allowed file size, authenticates/decrypts it, then invokes the existing trusted SQLite reconstruction. The transient decrypted buffer is cleared afterward. Wrong passwords, invalid authentication and shutdown produce no new stage or saved changes. The original uploaded artifact's SHA-256 digest remains the command identity; review/commit/replay do not require keeping a password. The existing staged plaintext database is private, session-bound and removed on cancellation, completion, expiry or shutdown.

Tests cover a fixed version-1 artifact, fresh randomness, exact bytes and passwords, authentication failures and bounds, cleanup, older SQLite input, cross-installation credential/history restoration, restart/replay and desktop/phone-sized password workflows. Download tests cover session isolation, native attachment names/lengths, HEAD, completed/interrupted transfers, expiry, bounds and shutdown cleanup. Chromium and Playwright WebKit exercise HTTP Connection/backup downloads. Native Safari 26.5 on the tested Mac still delays finalization after the transfer completes, including standalone plain-text downloads; the user reports immediate completion in the iPhone Home Screen app. The underlying macOS cause and a fix remain unverified. All automated fixtures use synthetic keys and temporary databases. These checks do not establish immunity to offline guessing, future scanner adaptation, broader actual phone behavior or native Windows/Linux qualification.
