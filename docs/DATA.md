# Data persistence and portable-file contract

Agent reference for content backup/import/wipe, schema compatibility, credential boundaries and protected downloads. Read before changing persistence/data APIs. Current constants and validators live in shared contracts and `backup-validation.ts`; tests use temporary real SQLite and synthetic keys.

Settings → Data backup exports a consistent portable SQLite snapshot, inspects uploads and imports their entire content after review. Import is append-by-identity with explicitly confirmed overlap replacement, not a file-level database overwrite. Application settings, languages, owner authentication and runtime authority remain separate. Local Connection keys and pre-upgrade snapshots are not application-encrypted; portable wrappers do not change that.

## Content backups

### Save and inspect

**Save...** opens a password dialog with both password fields visible from the start and **Save** / **Cancel** actions. **Save** uses SQLite's online backup API, including committed WAL pages and picture BLOBs. The downloaded `ORE-backup-<UTC timestamp>.orebackup` file encrypts the entire portable snapshot, including saved model API keys and schema/build/creation metadata. Enter an optional password and confirm it before saving. Keep a nonempty password separately; ORE cannot recover it. Leave the password blank for a deterrent against generic key scanners; anyone with ORE can open blank-password files, including through an automated decoder. Keep files private. See [protected file format and boundaries](DATA.md#protected-portable-files). The page reports when the snapshot is ready; the browser's download list reports the file download. It does not claim a disk save before the browser finishes.

The artifact excludes owner password hashes, login sessions, process ownership, library command receipts and data-management command receipts. Removed data is securely deleted from the private snapshot and its pages are rebuilt before download. Runtime state is never removed from the live database by exporting.

New-chat default bookmarks are application preferences stored beside the database, like Chat appearance settings. SQLite backups do not include them; import/wipe leaves the local preferences file intact. If a chosen record no longer exists, new chats use the original creation fallback for that category.

Under **Import backup**, use **Select file...** to choose a file, then enter its password in the dialog and choose **Import** to upload it to private server staging for inspection. This opens the existing review; importing saved content still requires the separate confirmation. Leave it blank for blank-password files or older plaintext SQLite backups. Authentication/decryption completes before SQLite validation or staging; a wrong password or damaged/unsupported wrapper changes no saved data and creates no stage. Errors appear inside the dialog. Correct the password and choose **Import** again to retry the same file. Failed attempts retain password fields and the selected file; successful download creation or inspection closes the dialog. **Cancel** or Escape dismisses an idle dialog and discards its passwords and selected file. While a request is running, the dialog stays open and prevents duplicate submissions or dismissal. Passwords are transient and never enter browser storage, receipts or the backup itself. The original encrypted upload digest identifies reviewed/imported commands. The source file remains unchanged. An inspection is bound to the uploading login session and expires after 30 minutes, even while open. Cancel, completed import, application shutdown and restart remove staging. Uncertain commands retain staging until explicit retry or expiry; successful command receipts survive restart even when staging no longer exists.

Invalid SQLite content shows “This file is not a valid ORE backup.” with a collapsed **Details** control. Expand it for the failed validation phase and a specific structural reason, including schema-object differences, record fields, constraint codes or coverage/dependency failures. Wrapper/password failures instead ask the user to check the password and retry in the dialog; they do not reveal whether authentication failed because of the password or damaged ciphertext. Diagnostics omit uploaded values, API keys, arbitrary schema names and raw SQLite/Zod messages. Failed inspection leaves the source file and current saved data unchanged; cancel the dialog and select another file to retry.

Branches load only when expanded. Chats have nested branches for their turns, variants, requests, memory, preparation and lore records. Global categories expose libraries, Connections, pictures and tag relations. Records are paged in groups of 40; branches fetch labels without loading text or image BLOBs. Leaf text fields are selected individually and fetched in 8,192-character pieces. API key nodes reveal only presence. Images come from authenticated local PNG resources. Text is displayed literally; remote URLs, HTML and instructions in a backup are never executed.

### Import and collisions

Review lists additions and overlapping identities, current dependent-record counts for replaced chats, blockers, and retained chats using incoming shared records. Review pages show at most 40 units/effects at once. Names are labels, not identity. Equal names with different IDs remain independent. Built-in IDs can overlap.

An overlapping chat is replaced as a whole: transcript, variants, generations and historical requests, memory versions and corrections, saved selection/cutoff, preparation history, and lore state/provenance. Current-only children are removed. An incoming library record replaces its text, links, local tag/picture associations and saved key presence/absence. An absent incoming key or picture clears the overlapping value.

Import requires explicit confirmation, naming the number of overwrites. Cancel changes no application content. Import retains unrelated records. Shared settings affect retained chats' future requests and advance their chat revisions, while preserving original turns, saved requests and narrative memory. Book overwrites retain only semantically unchanged entry matches (cosmetic labels/comments preserve them); character/persona name changes reset affected retained chats' lore epochs. Imported chats retain their own saved lore state.

Different tag IDs with the same normalized name block import. Rename the source or destination tag and create/review a new backup; identities are not silently merged or renamed. Cross-kind identities, cross-chat child ownership, broken selections/dependencies and incompatible unique constraints also block import. Storage-level picture collisions map incoming immutable assets to a separate internal identity, preserving bytes used by retained characters. Only unreferenced assets are cleaned up.

Save a backup before overwriting. Existing library copy/edit actions can preserve some records, but a duplicated character can share its lorebook. ORE does not yet provide an independent full chat-copy/branch workflow. This feature imports the entire backup; selective import and a separate Replace mode are outside its scope.

### Atomicity and recovery

Import/wipe require globally idle response/preparation work and exclusive mutation coordination. The server also blocks them while another command or asynchronous library/image/lore request is in flight. Cancellation must settle before these actions proceed. The browser's disabled controls are not the integrity guard.

Upload validation, trusted reconstruction and merged-state preflight run before the final transaction. A full destination-state SHA-256 token covers all portable tables and the dataset epoch, including child records and picture/tag state. Commit rechecks it inside the transaction. Any saved content change requires refreshed review. Coupled import/wipe changes, the new dataset epoch and the durable command receipt commit together. Constraint/write failure rolls back to the previous state and permits explicit retry. A synthetic child-process kill immediately before the command receipt write verifies recovery of the previous committed story.

Commands retain UUID identity and exact payload digests. Retrying an acknowledged or ambiguous successful command returns its original outcome without executing again, including after restart. Different data with the same command ID conflicts. A deliberate second import uses a new review/command. The browser stores only this command identity/digests for uncertain acknowledgement recovery, never backup bytes or API keys. Do not clear browser storage during uncertain recovery.

Migration 13 adds a durable dataset epoch and data-management receipts without changing source revisions. Every ordinary mutating API request carries the browser's captured epoch (`X-ORE-Epoch`). Before the first import/wipe, an omitted header means the legacy `initial` epoch; after it changes, omitted/stale headers fail. The request gate covers commands without numeric revisions too. Existing async mutations prevent import/wipe until they settle; server-owned response/preparation tasks are also checked. Restoring an old numeric revision therefore cannot validate an old client command.

Other tabs display a dataset-change notice and cannot save old edits. Copy unsaved library/turn editor text before reloading. Composer drafts stay in browser localStorage, outside the backup, with their captured epoch. After reloading, recovered nonempty drafts require **Use recovered draft** before an explicit send; old staged-send identities are discarded on that acknowledgement. No draft is automatically submitted. Drafts do not sync between devices and may be lost when browser storage is cleared/unavailable.

Running generation/preparation becomes interrupted in the portable artifact, retaining committed progress and saved partial reply/reasoning. Incomplete output does not become a response variant or complete a pending turn. Unapproved repair candidates are omitted; their steps become discarded, and awaiting review becomes interrupted. Historical model bodies, budgets, usage and approved summary versions stay unchanged. Internal generation/job request IDs are replaced and repair-command receipts are removed so historical retries do not become local execution authority. Import/restart never automatically calls a provider.

### Wipe scope

Wipe deletes all chats and their children, user libraries, Connections and API keys, pictures, tags, and content command receipts. It retains the local owner password/login, the requesting session, factory `default` prompt and `default-context` preset, dataset epoch and data-management retry receipts. Other sessions are revoked. It empties tables transactionally without deleting the open database file, and does not recreate a starter chat. Libraries and Settings remain usable for import or creating new content. This is not account reset, password reset or uninstall.

### Format and bounds

- New downloads use a version-1 encrypted `.orebackup` wrapper around a single SQLite file, portable format `ore-sqlite`, format version 1, current schema 15 and the creating build’s full commit hash (or `unrecorded-development` when unavailable). Earlier backups with package-version build labels remain readable and retain those historical labels.
- Supported older input: exact shipped ORE schemas 12, 13 and 14, tested with populated databases. A private trusted copy rebuilds them into schema 15, leaving unavailable library/message timestamps and generation translation metadata NULL. Current backups preserve these fields. Exact full schema-15 databases are also accepted without portable metadata; owner/runtime records are ignored. Other schemas, future versions and arbitrary SQLite files are rejected. Installation language packs and browser language preferences are outside the content backup.
- Uploaded/downloaded database size: at most 128 MiB, plus exactly 54 bytes of wrapper overhead for protected files. Old plaintext SQLite uploads keep their 128 MiB bound. Older ORE builds cannot open protected downloads; current ORE accepts both formats. At most 100,000 portable rows in the input and combined result; at most 16 MiB UTF-8 per text column; JSON nesting at most 100. Existing subsystem field limits still apply. Picture limits remain those in [picture contract](COMPATIBILITY.md#character-pictures).
- At most three staged inspections per server; each expires after 30 minutes. Staging reserves four times the input size plus 16 MiB of free disk headroom. Actual I/O errors still roll back/clean up rather than relying on the free-space estimate.
- Schema tables, columns, constraints, triggers and indexes must match shipped definitions after normalizing CRLF line endings to LF. This permits backups created with Windows or macOS/Linux migration-file line endings; all other SQL text remains significant. Unknown triggers, views, virtual tables and other executable schema additions are rejected. Uploaded schema SQL never runs against the destination. Only rows are reconstructed into a freshly created trusted schema, checked for types, references, constraints, selected variants, coverage and dependency cycles. Stored transcript and other content line endings are preserved.
- Validation and transactions are bounded but synchronous SQLite work can briefly pause API processing for large files. There is no background job, incremental half-import, scheduler, retention policy or automatic retry. Password derivation runs asynchronously with at most two concurrent protection/opening operations; export encryption streams from the private snapshot. Uploads retain the existing bounded in-memory binary handling.

## Protected portable files

ORE protects downloaded backups with standard password-derived encryption. The optional password may be empty. A nonempty password must be supplied exactly on import; it is neither embedded in the file nor recoverable by ORE. Password strength still matters against offline guessing. An empty password only deters scanners that look for directly readable API keys. An ORE-aware tool can open empty-password files automatically; targeted extraction need not remain manual.

Protection applies to the entire portable snapshot, including credentials, story text and metadata, and to exported Connection profiles. It does not change the live database, local schema-upgrade recovery snapshots, HTTP LAN transport, or ordinary character/persona/preset exports. Connection keys are excluded from profiles unless explicitly included; the wrapper authenticates the content kind separately from backups.

### Workflow and transport

Settings → Data backup → Save... opens a dialog with optional password and confirmation fields visible immediately. Keep it separately from the downloaded `ORE-backup-<UTC timestamp>.orebackup` file. Under Import backup, select the file first, then enter the same password in the dialog and choose Import to inspect it. Failed attempts show errors inside the dialog and preserve its fields and selected file for explicit retry. Successful creation/inspection closes the dialog. Cancelling the dialog or closing Settings discards these transient values. No password is stored in localStorage, command receipts, request history or the artifact.

Authenticated, same-origin POST `/api/data/backup` accepts `{ "password": "…" }`. With `Accept: application/json`, it returns a prepared download link and filename; the browser follows that normal HTTP link instead of creating a Blob URL. The subsequent authenticated GET `/api/downloads/:token` sends the completed encrypted file with an explicit content length and attachment filename. This avoids Blob URL lifetime dependence. Native macOS Safari has separately reproduced delayed finalization even for standalone plain-text HTTP downloads; HTTP completion and Playwright download completion do not establish native disk finalization. Do not weaken security or change encryption on an unconfirmed OS/network hypothesis. Direct POST callers without that Accept header still receive the binary file. Passwords never enter URLs. Binary POST `/api/data/stages` carries an optional `X-ORE-File-Password` header containing canonical base64 of the exact UTF-8 password. An absent/empty header means an empty password. Base64 only transports the header; it provides no additional secrecy. Existing application authentication, origin checks and transport policy still apply. Application request logging remains disabled.

Passwords are limited to 256 UTF-16 code units, matching the input and shared validator. There is no trimming, normalization or minimum length. The receiving installation does not need the sender's owner password or other local settings. After successful opening, the existing shipped-schema/content validation, paginated inspection, explicit import confirmation and transactional recovery apply. Existing plaintext SQLite backups remain accepted. Older ORE builds cannot read the new wrapper.

### Version 1 wire format

All lengths are bytes. No JSON, compression or executable metadata is outside the ciphertext.

| Offset | Length | Value |
| --- | --- | --- |
| 0 | 8 | ASCII `OREENC\r\n` |
| 8 | 1 | Wrapper version: 1 |
| 9 | 1 | Content kind: 1 for a backup, 2 for a Connection profile |
| 10 | 16 | Cryptographically random scrypt salt |
| 26 | 12 | Cryptographically random AES-GCM nonce |
| 38 | Payload length | AES-256-GCM ciphertext |
| End − 16 | 16 | GCM authentication tag |

Derive a 32-byte key using Node's scrypt implementation with the exact UTF-8 password, the stored salt, `N = 32768`, `r = 8`, `p = 1` and a 64 MiB working-memory ceiling. These are fixed version-1 parameters; uploaded files cannot request different work factors. Use AES-256-GCM with the 38-byte header as additional authenticated data and an explicit 16-byte tag. Each export generates fresh salt and nonce, even with a blank or repeated password. Future incompatible parameters require a new wrapper version; preserve version-1 reading.

The wrapper adds exactly 54 bytes. Backup plaintext remains bounded to 128 MiB; the HTTP/browser file bound allows those additional bytes. The wrapper version is independent of the inner portable format and SQLite schema version. Unsupported versions/kinds, malformed structure and oversized payloads fail before key derivation; incorrect passwords and failed authentication fail before any bytes reach SQLite. The authentication tag detects damage but does not establish a file's publisher. Imported content remains untrusted and must pass the ordinary validation.

### Connection profiles

Libraries → Connections offers **Export...** on each saved profile and **Import Connection...** in the toolbar. Export asks for an optional password and an unchecked **Include API key** option; checking it shows the credential-sharing warning. Save downloads `<name>.oreconnection`. Selecting an import file opens a password dialog; incorrect passwords preserve the selected file and fields for explicit retry. Cancel discards transient values. Pending submission prevents duplicate requests and dismissal. Imported profiles receive new identities and local dates without changing existing Connections, defaults or chat selections.

The inner UTF-8 JSON is `{ "format": "ore-connection", "version": 1, "connection": { … }, "apiKey": "…" }`, with `apiKey` omitted unless explicitly included. Settings and keys pass existing Connection validation; extra fields, including uploaded identities/revisions, are rejected. Plain JSON profiles are unsupported. Inner plaintext is bounded to 128 KiB, with a 54-byte wrapper allowance. Export and import share the backup encryption parameters, exact password behavior and two-operation derivation limit. Small profiles use buffers instead of temporary plaintext files; plaintext buffers are cleared after use.

Authenticated same-origin POST `/api/library/connections/:id/export` accepts `{ "password": "…", "includeApiKey": false }`, with both fields optional. Like backup export, `Accept: application/json` prepares a normal HTTP download; other callers receive the encrypted bytes directly. POST `/api/library/connections/import` accepts `{ "revision": 0, "password": "…", "base64": "…" }`; bounded canonical base64 transports the encrypted bytes in JSON. Passwords never enter URLs or persisted commands. Successful import creates the profile/key in the existing short library transaction after decryption and validation, rechecking the captured revision and idle state. Failed writes roll back the whole profile. Retrying a successful command with its old revision fails without creating a duplicate. An uncertain acknowledgement requires inspecting Connections before starting another import. Connection and backup kinds cannot be opened interchangeably. No schema migration is needed.

### Ownership and recovery

`src/shared/protected-files.ts` defines browser-safe bounds and format constants. `src/server/protected-files.ts` owns password transport validation, asynchronous scrypt, encryption/decryption and a process-wide bound of two simultaneous operations. Derived key buffers are cleared on every exit. No new dependency is required. Busy operations return an actionable error and require explicit retry.

Backup export first creates and sanitizes the existing private consistent snapshot, then streams it into a separate private encrypted file. Downloads receive only completed ciphertext. Successful encryption removes the temporary plaintext snapshot; direct download close or failure cleans its download directory. Encryption failures remove partial output and never fall back to a plaintext download. These are private temporary files, not a claim of physical secure erasure.

`src/server/downloads.ts` owns at most four pending prepared downloads. It retains only encrypted Connection buffers or completed private encrypted backup files, plus filename, length, expiry and a hash identifying the requesting session. A random 256-bit URL token also requires that same authenticated session; another session cannot use it. Prepared downloads expire after five minutes, with cleanup every 30 seconds and on access/shutdown. A completed GET consumes the link and releases its data; HEAD does not consume it. An interrupted transfer remains retryable within its expiry. Existing readers may finish before expired files are removed. No password, API key plaintext or persistent ticket record is retained. A server restart invalidates links; export again. `src/web/downloads.ts` validates the local download URL and filename and starts a normal HTTP attachment download without a Blob URL or revocation timer. The interface reports that the browser handles completion, rather than claiming the file has reached disk.

Import buffers at most the allowed file size, authenticates/decrypts it, then invokes the existing trusted SQLite reconstruction. The transient decrypted buffer is cleared afterward. Wrong passwords, invalid authentication and shutdown produce no new stage or saved changes. The original uploaded artifact's SHA-256 digest remains the command identity; review/commit/replay do not require keeping a password. The existing staged plaintext database is private, session-bound and removed on cancellation, completion, expiry or shutdown.
