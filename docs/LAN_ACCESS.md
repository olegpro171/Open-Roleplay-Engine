# HTTP LAN access

The 2026-10-21 decision permits HTTP on a trusted LAN and defers HTTPS configuration. Application Settings → Phone / LAN access contains the enable toggle, default-on Select network automatically checkbox, read-only hostname address and recovery controls. Unchecking automatic selection reveals the network and port fields. Configure these from the local loopback URL on the server computer after creating the owner account. Phone views are read-only for this section. Changes apply on Save without restarting ORE. The normal local listener stays available independently.

## Admission and scope

`lan-policy.ts` enumerates non-internal RFC1918 IPv4 addresses with contiguous /8–/30 masks, excluding common tunnel and virtual adapter names. Automatic mode keeps a working binding; after a change it prefers the same adapter name, then chooses the first eligible interface in stable ID order. Port is always 3000 in this mode, including when a command supplies another port. Manual mode retains an explicit network/port. Interface names do not universally identify hardware; IPv6-only, public-address-only and /31–/32 interfaces are outside this feature.

`LanAccess` delegates native socket handling to `lan-listener.ts`, binding a separate HTTP server to the selected address/port and dispatching admitted requests through `app.routing`. Authentication, commands, SSE and operations are shared. Each request requires current listener authority, its exact socket local address, the exact local hostname:port or bound IP:port Host, and an actual loopback or private same-subnet peer. Forwarded headers do not establish trust. This listener cannot create the owner account or modify LAN settings, even from the server computer itself; use the normal local URL.

`lan-hostname.ts` reads macOS’s Bonjour LocalHostName using a bounded scutil call and normalizes it to a valid lowercase `.local` name. The displayed address is consequently stable across DHCP changes, for example `http://macbook-pro-oleg.local:3000`. macOS supplies mDNS/Bonjour discovery; ORE does not install or implement a DNS service. Phones and the local network must permit mDNS resolution. Other host platforms use their OS hostname and need an existing hostname responder; their setup remains unqualified. Changing the computer’s name changes the URL. Direct IP access remains admitted for diagnostics. The host allowlist accepts no arbitrary aliases or subdomains.

Origin/content-type checks, session authentication, HttpOnly/SameSite=Strict cookies, credential exclusion and CSP remain active. HTTP cookies cannot use Secure. Passwords, session tokens, chat data, backups and newly entered credentials lack transport encryption on the LAN hop. Outgoing provider transport continues using each Connection's endpoint independently. No proxy, router port forward, certificate or external service is configured. A router/tunnel that proxies or rewrites client addresses can defeat assumptions about a physical LAN boundary; do not expose ORE through such an intermediary. Firewall permission, Wi-Fi device isolation and keeping the server awake remain host/network responsibilities.

## Saved state and failure handling

The version-2 `<database>.lan.json` sidecar holds a settings revision, enabled and automatic flags, interface ID/port, and captured manual binding. Version 1 upgrades atomically to automatic selection/port 3000 while retaining enabled state and revision. Explicit version-2 manual choices survive restarts. No authentication secret is stored here. It is private on creation (0600 on POSIX), remains outside SQLite content, and is excluded from Git and portable releases. It survives application updates and data import/wipe; database backup download/import does not copy network enablement. Moving a database file alone does not move this configuration.

Saves validate shared Zod contracts and require authenticated local access. One queue serializes settings changes and recovery; captured revisions reject competing/stale commands. Manual mode prepares a replacement listener before writing a unique flushed temporary file and atomically renaming it to the sidecar. New-listener requests remain denied until the commit. Bind/write failure retires the prepared listener and preserves the previous configuration/listener. Automatic mode persists enabled intent before trying to bind: offline/busy startup yields an unavailable runtime status but does not require another browser command to recover. Failed file writes preserve previous settings in both modes. An uncertain save response is reconciled with Reload LAN settings, and the form retains edits on failure and ignores stale status responses across saves.

Disabling access commits after earlier queued work, removes listener authority and destroys LAN sockets, including SSE observers, before acknowledging completion. Already accepted asynchronous commands and server-owned generation/preparation continue. Shutdown immediately revokes authority, waits for in-flight binding work and discards late results. Every request and monitor tick rechecks interface identity/address/netmask; stale bindings close before replacement. The three-second monitor continues through offline periods, listener errors and occupied port 3000 in automatic mode, including with no browser open. It stops on disable/shutdown. Automatic runtime rebinds do not rewrite settings or bump their revision. Manual mode retains local recovery after a binding becomes unavailable. Local application access remains available throughout.

Malformed/unreadable saved settings fail closed and expose a local error. Explicit Save replaces that configuration. A power failure cannot make an uncommitted listener survive a process restart; startup uses only the saved file. This does not claim full filesystem durability against every hardware failure. Legacy explicitly configured HTTPS startup disables the HTTP settings; certificate provisioning/renewal and proxy integration remain deferred.

## Verification and manual acceptance

`tests/lan.test.ts` uses real temporary SQLite databases, isolated loopback LAN fixtures and the local mock provider. It checks default-off behavior, authentication and cookie flags, host/origin/peer admission, local-only setup/configuration, stale/concurrent saves, occupied ports, failed file writes and prepared-listener cleanup, restart/network-change recovery, malformed configuration and disconnecting an observer while generation completes. Policy checks cover private same-subnet and off-subnet addresses; fixtures do not represent an actual phone or physical Wi-Fi boundary.

`tests/lan-automatic.test.ts` uses the real controller/configuration path, controlled interface snapshots, a transport boundary double and a controlled interval clock. It checks fixed port 3000, sticky selection, DHCP/subnet/interface changes, offline startup, occupied-port and listener-error retries, disabled/stopped cleanup, late binding results and version-1/2 compatibility. This isolates asynchronous policy without changing OS interfaces or binding a potentially occupied user port. Native transport/admission and hostname-based login remain covered by the real socket tests.

`tests/uuid.test.ts` reproduces the original failure when HTTP lacks randomUUID and verifies valid distinct UUIDv4 command identities using getRandomValues. The browser LAN workflow routes a synthetic insecure origin to the owned test LAN listener, verifies the browser really lacks randomUUID, signs in separately, recovers a composer draft, sends a turn and checks read-only phone settings. Host/origin admission is exercised separately by server socket tests; synthetic-origin routing does not establish actual DNS or Wi-Fi connectivity. Desktop and phone settings rendering is checked through Playwright screenshots and overflow assertions.

A separate local smoke check bound the Mac's real `en0` private address using a temporary empty SQLite database and synthetic owner password. Session inspection, LAN login and authenticated chat reads returned 200; disabling access closed that listener and left local access available. The client ran on the same Mac, so this establishes real interface binding and local routing, not reachability from a phone or another physical device. No active user database or real provider was used.

The automatic-mode smoke check also used the actual `http://macbook-pro-oleg.local:3000` hostname through the system resolver. Session inspection, hostname-origin login and authenticated chat reads returned 200. Temporarily hiding interfaces from the controller's inventory closed access; restoring that inventory reopened the native listener and the same hostname/session worked again. This was a simulated inventory outage with real binding and Bonjour resolution, not a physical DHCP/Wi-Fi change or a phone test.

For manual acceptance, stop the previous ORE process and launch the changed build. On the local page, open Settings → Phone / LAN access, leave automatic selection checked, enable access and save. On a phone, bookmark the displayed hostname URL, sign in, open a chat and send a turn. Check keyboard/scrolling, reload, background/foreground reconnect and shared state on the Mac. Disable LAN while observing a running response; the phone should disconnect, while the Mac retains the response. Re-enable and reconnect to inspect saved progress. Check restart and recovery after DHCP changes/network outages without opening Settings to trigger recovery. These physical-device steps remain unverified until performed.
