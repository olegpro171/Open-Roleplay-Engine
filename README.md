# Roleplay Engine

A personal roleplay application with the in-app name **ORE**, currently hosted locally on this Mac. Persistent chat and the second milestone—roleplay libraries and imports—are implemented for local testing: reusable Connections, characters, personas and prompts; multiple chats; streaming; turn editing; cancellation/retry; and saved request inspection.

The **third milestone**, durable layered compaction, is implemented for local testing: prepare imported sessions, inspect a layered timeline, edit summaries, and review targeted repairs. Context presets select a separate summarization Connection and editable extraction/compression prompts. Normal generation prepares context when needed. The standalone Python visualizer remains available; see [VISUALIZER.md](docs/VISUALIZER.md).

Generated summaries are checked for obvious refusals, placeholders, empty output, repetition loops and incomplete/truncated responses before they can replace source context. These are basic heuristics, not verification of summary facts. Real-model narrative quality and actual phone use remain unverified.

## Start on this Mac

Double-click **start-app.command**, or run:

```sh
./start-app.command
```

This launcher checks the latest `main`, builds only when the installed commit changes, and starts ORE with its private Node runtime. It keeps a managed source checkout and replaceable application files under `ore-portable/`; your source checkout is left intact. Existing source-launcher data remains in this checkout's `data/roleplay.sqlite`; the default is stored relative to the repository so moving or renaming the whole folder keeps the same saved chats. Established external databases that disappear cause a recovery error instead of an empty replacement. No global Node/npm is required. Leave its terminal open and stop with Control-C. Linux uses `./start.sh`; actual Linux qualification remains pending.

New builds must start the real server/UI against a temporary database before activation. Retained versions can be inspected with `./recover-app.command --list` and selected with `./recover-app.command --previous`; recovery checks schema compatibility and pauses automatic updates. See [safe version/database recovery](docs/RELEASES.md#database-upgrades-and-recovery) for restored snapshots and legacy paths after moving a folder.

In Safari on the Mac, open that address and choose **File → Add to Dock**. The tab favicon and Dock icon use the current ORE header mark. If ORE was already added to the Dock with an older icon, remove that web app and add it again to pick up the new artwork. Icon PNGs are generated from `artwork/ore-mark.svg` with `node scripts/generate-icons.mjs` using the supported Node runtime.

On first launch, create the owner password on the Mac. Open **Libraries → Connections**, create a Connection with your API base URL, model identifier and optional API key. Create/import characters and personas in their libraries, then select them under **Chat settings**, or use **Libraries → Chats → New chat**. Write a turn on **Story**. Its left sidebar opens **Chat settings**, **Inspect memory** and **Request inspector**. Each tool keeps the current chat sidebar beside its content. Chat settings offers **Save and return** or **Return without saving**; the other tools offer **Return to chat**. On narrow screens, open **Chat details** in the header to see chat information and the three chat-tool buttons in a larger scrollable dropdown. Save/return controls stay visible above their page content. Use Request inspector to examine a saved attempt or preview the next request.

Saved data lives in `data/roleplay.sqlite`. Failed, cancelled and interrupted first responses leave their existing turn pending; regeneration keeps the completed selected response. Cancel sits to the right of the version selector under the generating turn for both first responses and regeneration; there is no separate Generating panel. First responses show a disabled 1 / 1 selector immediately, and the selector remains beside Regenerate response after completion. Cancelling before text arrives shows “Generation cancelled.”; any partial output remains visible. The “Last turn is still pending.” panel and Retry response stay available. Retry that response or delete the entire turn before sending another. Partial output is visible for inspection, but cannot yet be accepted as a completed response. Clearing either part of a completed turn preserves its completion and membership. Submissions, successful AI responses, copied greetings and part edits remove blank lines at the beginning and end while retaining internal paragraph breaks and indentation. Existing history and imported transcripts are not rewritten; a blank submission is rejected and whitespace-only model output leaves the turn pending.

Story renders Markdown in greetings, both turn parts and streaming replies: emphasis, headings, lists, blockquotes, links, code, tables and strikethrough. Quoted speech, including its quotation marks, appears bold in light blue. Em dashes stay outside speech styling everywhere, including before resumed dialogue and inside quotations. A separate heuristic handles Russian em-dash dialogue and recognized author interruptions, including the supplied examples; unfamiliar or ambiguous prose can be misclassified. Editing and model requests retain the original Markdown. HTML is shown as inert text, and image syntax shows alt text without loading remote images. The color is currently constant; Russian detection can be disabled independently in the renderer. See [chat formatting](docs/CHAT_FORMATTING.md) for details.

## Libraries, prompts and chat import

Libraries uses the same two-column workspace as Story: select a category in the left sidebar to see its list and editors in the larger panel. The last category is remembered in this browser when returning from Story or reloading. On narrow screens, the categories wrap above the content. Each list has a search box directly below its actions. Search matches names/titles, descriptions where available and Connection models; lorebooks also search entry names, comments, keys and content. Character search combines with selected tag filters. **Import lorebook** sits beside **New lorebook** and opens the existing review before saving.

New Connections start with 8,196 reserved output tokens; this is editable per Connection and does not change existing records.

Library editors place **Save …** and **Close editor** in a vertical stack in the left sidebar, above the content on narrow screens. Nonempty multiline fields open tall enough for their text, up to four times their usual default height; short text uses less space, empty fields keep the default, and manual resizing remains available. Failed saves retain the current draft.

In the character editor, optional **Title / comment** distinguishes same-name versions: “Alice · University version” and “Alice · Medieval version”. The local, searchable label appears in Libraries, character selectors and Story headings; new chat titles copy it once. It is saved separately from Name (up to 200 characters on one line), copied on duplication and removed by clearing the field. It never enters prompts, `{{char}}` substitution or card exports, and is independent of creator notes and V3 nickname. Editing only this label preserves chat revisions, saved memory, lore state and existing chat titles. Older characters start with no suffix.

Each turn groups its available controls in one row below the response, beside the **‹ current / total ›** version selector: **Regenerate response** / **Cancel**, **Edit input**, **Edit response**, **Show reasoning** and **Delete turn**. Show reasoning appears when that response/attempt has readable reasoning. The empty input of a copied greeting stays hidden. Desktop labels become compact icons as space narrows; icons retain accessible names and hover titles. On phones the selector stays visible, and the actions scroll horizontally on especially narrow screens. Deleting still asks for confirmation.

**Regenerate response** under the latest completed turn saves and selects another response when generation succeeds. While regeneration runs, the assistant area shows “Waiting for first token…” and then streams the new text directly in the turn. Cancel replaces Regenerate response in the turn while regeneration runs. Cancelling quietly restores the saved response and button; failures and interruptions still show an error. The saved response remains selected until success and reappears on failure/cancellation/interruption. Regeneration uses the saved input and current setup, excluding the old response; unsent composer text is not submitted. Saved variants use a compact **‹ current / total ›** selector under the turn. Arrows immediately select the previous/next response; type a version number and press Enter or leave the field to jump. The right number counts response versions for that turn. Invalid input and Escape restore the current number without changing the story. Variants remain available on older/archived turns, but only the latest turn can generate new ones. Each generated variant retains its own request and usage. Later turns stay unchanged. Selecting another variant starts fresh lore activation history; successful regeneration commits its new admissions once.

If a summary represents A, selecting a different B marks it out of date. Selecting unchanged A again restores freshness without repair, unless other sources/dependencies changed. A summary already repaired against B remains out of date when A is selected. Typing a version number does not affect memory until the selection is submitted. Regeneration preparation keeps the live memory selection/cutoff unchanged; a direct manual correction containing the latest response must be resolved explicitly first. New chats copy character alternate greetings into the opening turn’s response versions.

- **Personas:** create/edit name, local **Title / comment**, and description; import SillyTavern persona-backup JSON or a basic `{ "name": "…", "description": "…" }` object. The title helps distinguish same-name personas in the library, selectors and Story labels; it is excluded from prompts and exports. Export uses SillyTavern's persona-backup shape. Avatars and SillyTavern positioning/locks are not imported.
- **Characters:** create/edit name, description, personality, scenario, greeting, alternate greetings and example dialogue. Import legacy/V1, V2 or V3 JSON, or PNG cards with embedded `chara`/`ccv3` text metadata (prefer `ccv3` when both exist). Export V2 JSON for legacy/V2 cards and preserve V3 format for imported V3 cards. Embedded V2/V3 lorebooks become independent library books linked as the character default, atomically with import. Card instructions follow the explicit preset permissions described below. Other imported extensions, assets and nicknames remain preserved and inactive. Older cards expose **Extract embedded lorebook** without changing existing chats. This is the documented lorebook profile plus basic card fields, not full V2/V3 card compliance. JSON cards are limited to 2 MB; image-bearing PNG cards to 10 MB. Imported PNG artwork is retained separately from card metadata.
- **Prompts:** add text blocks or markers, collapse each block, set message roles, enable/disable, drag to an indicated insertion line or use the up/down buttons. Expand Character to check **Name, Description, Personality, Scenario and Example dialogue**. Checked nonempty fields become separate messages in that fixed order with the marker role, exactly like adjacent individual field markers. Greeting remains the copied opening turn. Prompt peek groups Character's individual messages. Enabled blocks/markers compose the base prompt; the selected lorebook adds conditional entries relative to included fields or Messages. Summary inserts selected historical memory at its configured position and role; Messages inserts the managed verbatim tail with its original roles. Without Summary, Messages inserts the newest whole turns that fit the complete input limit, ignoring the saved memory cutoff. Missing Messages sends no turns. Generic missing-source warnings are advisory; empty presets and empty Character selections may be saved, but empty resolved input fails before a model request. At most one enabled Summary and Messages marker each is supported. Duplicate, export/import, edit the built-in default, or use **Restore original**. The current default and new-prompt template are Card system prompt → Character → Persona → Summary → Messages → Card post-history instructions. The system marker uses the former Instructions text as fallback; the closing fallback is empty. Messages permits character depth injection in new templates. Existing saved presets keep their current blocks and permissions. New prompts receive independent copies of the factory template.
- **Names:** case-insensitive `{{user}}` and `{{char}}` resolve once in prompt text and card/persona fields using selected names (fallbacks: You / Character). `{{original}}` resolves only inside the two card instruction fields to their marker’s fallback; other macros stay literal. Stored conversation text is not reprocessed. New chats copy and resolve the character's primary and alternate greetings into one completed opening turn with response versions in card order. The primary is selected first; blank greetings are skipped, and if the primary is blank the first nonblank alternate is selected. If all are blank, no opening turn is created. Duplicates stay available. Later card edits do not change saved greetings. Its empty user bubble is hidden. In the character editor, use **Add alternate greeting**, edit its text, or **Remove greeting**, then **Save character**. Older imported cards expose their preserved alternatives without reimporting. Up to 1,000 alternatives of 100,000 characters each are supported; malformed preserved alternatives remain exportable and can be explicitly cleared in the editor before starting a new chat.
- **Chats:** **Libraries → Chats → New chat** asks only for Character and Persona. **Create chat** saves the chat and opens **Chat settings**, with “[Character display label] - Roleplay” already saved as its title. You can leave immediately with defaults or edit and **Save and return**. Without a character the title is “A new story”; long names are shortened to fit the title limit. Each chat keeps its own selections and target. Shared prompt-bearing library edits affect future requests in all selecting chats; saved requests and copied greetings keep their historical text. Shared edits are blocked while any response or preparation runs. Referenced library items cannot be deleted until chats/presets stop selecting them. Switch chats through **Libraries → Chats**. Any idle chat can be deleted, including the original or final chat; deleting the current chat keeps the library open. Generation and pending-turn blocking are per chat.
- **Replace history:** under **Chat settings**, choose a SillyTavern-style `.jsonl` file, review the message/turn counts, then click **Replace all messages**. Only active `mes` text and `is_user` roles are imported. Foreign summaries, memory snapshots, alternate swipes, sender metadata and `hiddenFromAI` flags are excluded. The complete active transcript is imported, including messages previously hidden by another application's compaction. Chat selections remain unchanged; old turns and their request records are replaced together. No greeting is prepended.

Chat imports stream-read files up to 128 MB, with at most 50,000 messages, 100,000 characters per message, 8 million characters per JSONL line, and 20 million active text characters total. Invalid/unsupported input, stale chat revisions and active generation leave saved history unchanged. System messages are rejected rather than silently reclassified. Ordinary user/assistant entries form turns; consecutive same-speaker entries retain separate turns with an empty opposite part. Historical turns are complete; only a final unpaired user entry awaits a response. An optional leading SillyTavern metadata record is ignored. This is a text transcript importer, not restoration of another application's memory or group-chat state.

The version-2 database migration retains the existing chat, turn/part identities, revisions, credentials and saved request records. Existing inline character/persona/instructions become reusable records. Version 3 adds context state, summary versions, preparation jobs and saved steps without rewriting transcripts or enabling model calls for existing chats. Version 4 adds nullable provider token usage to generation records; old requests retain their original bodies and have no retroactive usage counts. Version 5 adds Summary to an exact untouched old default, preserving edited defaults and all other presets. Version 6 upgrades extraction/promotion fields that exactly match the previous factory text, preserving custom prompts and settings, repair instructions, saved memory and historical requests. Version 7 adds lorebook command/state/provenance storage and upgraded the exact untouched old factory prompt with lore controls. Its existing chats kept None and saved inactive embedded books required explicit extraction. **Version 8 removes those lore controls from every saved preset and gives unconfigured Character markers all five fields.** Remaining block order/roles/text and explicit selections are preserved. A selected book now uses automatic placement and system defaults even if old lore controls were disabled or customized; select None to disable lore. Separate Character messages change framing/token estimates. The upgrade is transactional and leaves historical requests, activation state and saved memory untouched. Older prompt-file imports receive the same conversion. Restore original explicitly installs the current factory template. Replacing history clears that chat's old memory and preparation records atomically. Stop the previous server before launching the updated application; the launcher does not modify original export files.

## Card instructions and Chat Settings warnings

Open a character's **Card instructions** disclosure to edit its system prompt, post-history instructions and Character's Note text/depth/role. Already imported cards expose their preserved fields without reimporting. In a Prompt preset, add **Card system prompt** and **Card post-history instructions** markers where wanted, choose their roles and optional fallback text, and check **Allow character depth prompt injection** under Messages to permit the note. Missing permission means off for older presets. Restore original explicitly installs the current template, including both markers and permission.

A nonblank card instruction replaces its marker's fallback; `{{original}}` includes that fallback. Depth zero follows the newest outgoing history message; one precedes it; larger depths clamp before the oldest included message. Lore and summaries do not count toward depth. Input estimates include all instructions and framing; no note is discarded to fit. Instructions never become saved turns or summary sources.

**Chat settings** shows the saved warning count. Its warnings list follows the displayed source selections and explains excluded card instructions, invalid card settings and lore entries without usable destinations. Buttons open the relevant library editor. Deliberate omissions remain advisory; malformed actively consumed values fail before a model call. Prompt peek explains current lore matching/cap outcomes and shows resolved card/fallback/depth provenance. [Full behavior and compatibility](docs/CARD_INSTRUCTIONS.md).

## Lorebooks

Open **Libraries → Lorebooks** to create, edit, search, duplicate, import/export or delete an unused book. The editor shows one selected entry at a time with searchable pages, separate human-only names/comments, book scan depth/cap/recursion, matching, placement, roles and priority/order. Shared edits affect future requests in chats selecting the book. Failed saves/conflicts retain the visible editing draft.

Standalone JSON import offers a review before commit. It accepts V2 books, the V3 `lorebook_v3` envelope and World Info entry maps or unambiguous legacy arrays; detection uses structure. Files are limited to 5 MB and 2,000 entries, with 100,000 characters per content/comment field, 64 keys per key group and scan/depth controls up to 1,000 messages. Character JSON imports are limited to 2 MB and PNG cards to 10 MB, with separate 2 MB embedded-metadata bounds. Oversized or malformed input fails without partial records. Unsupported extras are reported and preserved inactive. Lost acknowledgements reuse the import command identity; intentionally importing again creates an independent book. Export preserves the imported format or uses V3 for a new book.

Choose a character's **Default lorebook**, or None, and use **Open book** to edit it. A new chat prefills that default; its **Lorebook** selection is saved independently. Changing character in Chat settings preserves the current book. Duplicating a character shares its link; duplicating a book creates independent entries. Selecting None changes future requests without touching history or memory. Unlinking a character removes its book from future character exports. Linked/selected books explain their uses and cannot be deleted until those links are removed.

New books start with the latest four eligible messages, a 2,048-token lore cap and recursion off. Scanning uses original nonblank user/assistant messages, including pending/unsent input and copied greetings, independently of archived status. Literal matching uses NFC-normalized substrings, case-insensitive by default; regex requires an explicit setting and executes in bounded isolation. Descriptions/comments never become lore prose. Only `{{user}}` and `{{char}}` resolve once; other macros stay literal with notices.

Whole entries are admitted by priority descending, constants first on ties, insertion order ascending and source order. Final insertion follows insertion order. Constants obey the cap and available destinations. Only admitted/placeable lore triggers recursive entries. Selecting a book authorizes automatic placement: before the first/after the last included character source, beside the first corresponding included field, or within Messages by depth. Empty/unchecked fields and missing Messages make their destinations unavailable, with inspection explanations; history lore does not implicitly move elsewhere. Lore defaults to system; entries/decorators can override role, depth and supported field positions. Lore consumes fixed input before history planning. The standard pressure-optional directive gets one preliminary exclusion pass; final lore stays frozen during preparation/reuse. Required-input overflow fails clearly.

**Prompt peek** and **Request inspector** show Lore allocation and paginated entry outcomes, resolved text, destinations, roles, reasons and exclusions. A saved attempt retains its original data after edits/unlink/deletion; older requests identify lore metadata as unavailable. Preview/preparation do not advance standard prior-match state. Only successful response completion commits it. Semantic lore edits reset affected entry state; transcript/name/character/persona changes reset the chat's activation epoch. Memory-only changes preserve it. No live lore is sent to summary extraction, promotion or repair, and lore edits do not invalidate those summaries.

See [LOREBOOKS.md](docs/LOREBOOKS.md) for the decorator/extension matrix, ambiguity interpretations, recovery rules and safety limits. Probability/groups/sticky/cooldown/delay and other World Info engine extras stay inactive; full SillyTavern equivalence, semantic relevance and real-model recall are not claimed.

## Prepare an imported roleplay session

1. Create a summarization Connection in **Libraries → Connections**. It may use a different model or the same reusable Connection as roleplay.
2. Open **Libraries → Context presets**, edit the supplied preset or create one, select its summarization Connection, and save its settings/prompts.
3. Import the transcript through **Chat settings**, then select the context preset in Chat settings or **Memory**. Set the chat's input target.
4. Open **Memory**. **Save next summary** performs one budget-driven step, reusing a valid saved replacement when available. **Prepare chat** first reconsiders saved memory for the current budget, then continues until the assembled input fits. Model calls are made only for missing summaries needed to fit. **Stop preparation** retains completed replacements. Resume explicitly after cancellation, failure or server interruption; interrupted calls are never automatically repeated.
5. Inspect summary spans, source coverage, saved preparation steps and summary request bodies. Historical timeline navigation only changes the view. Later turns are not added to earlier job snapshots. New response requests remeasure the complete input, including pending user text, and prepare further if necessary.

**Summaries are disabled** when the selected prompt has no enabled Summary marker. Roleplay uses recent original turns only where Messages appears, including previously archived turns if they fit. Fixed prompt content and pending input consume the budget first; keep whole recent turns without truncation or skipping oversized recent turns to include older ones. Some capacity may remain unused. If required fixed content and pending input cannot fit, sending fails. No preparation or repair calls run in this mode; unused stale memory does not block a response. Saved summaries and preparation history stay intact. Enable Summary and use Prepare chat to resume, reviewing stale memory first. These recent-turn selections never modify saved memory. Compaction settings below apply to managed history with Summary enabled.

The editable starting values match the lab: minimum tail 8 completed turns, fixed batch 3 turns, requested summary size 750 tokens, promotion group 3 summaries and retained floor 3 per source level. They are starting values, not validated quality defaults. Keep all history verbatim while it fits; under pressure summarize complete oldest batches without dropping below the minimum tail. Residual turns stay verbatim. Promote only when no first-layer batch is eligible, using actual active-layer sizes and the accepted geometric-pressure rule. Stop as soon as input fits and preserve the committed selection across requests and restarts; spare capacity does not reactivate children.

The default extraction prompt creates a standalone continuity memory for each turn batch, prioritizing lasting outcomes, changes and unresolved matters. The separate promotion prompt consolidates ordered summaries, merging repetition and collapsing completed arcs while preserving consequential transitions. Both return plain summary text in the source language. Earlier memory only clarifies references. Promotion also aims for 40–60% of source-summary word count where compatible with the configured token target; neither target justifies dropping essential continuity. Prompt instructions cannot guarantee model fidelity. Existing factory prompt fields update on the next server start; custom wording stays saved and can be changed in **Libraries → Context presets**. Existing summaries are not regenerated automatically.

The summary-size setting is a soft prompt target. The summarization Connection's reserved output controls the actual `max_tokens` and physical input/output check; it is not subtracted from the roleplay input target. Aim below that output reservation to avoid truncation. Instructions and the entire fixed source batch must fit the summarizer's window; sources are not silently split or truncated. Up to three preceding selected summaries are included for reference when they fit, with explicit revision dependencies. Repair preserves its original earlier dependencies, using their current approved versions and explicit before/after changes when their text differs. Later events are never supplied as prior context. Generated output must reduce the complete roleplay input before a normal compaction replacement is committed.

Archived turns remain readable and editable. Edits/deletions invalidate dependent memory, including higher layers and summaries that read changed earlier context. Roleplay pauses while selected memory is stale. **Repair summaries** opens a continuous review dialog showing approved/remaining counts. Matching text panes align and highlight changes; edit the proposed summary, navigate differences or collapse unchanged passages. Expand **Why this needs repair** to compare previous/current sources and earlier memory. Phone screens use a unified comparison. **Approve & Next** saves the correction and generates the next required replacement using approved dependencies; the final button is **Approve & Finish**. **Regenerate** requests another candidate, preserving a valid existing candidate if generation fails. **Close** stops any running request and discards the unapproved candidate and your edits; approved repairs stay saved. Reopen with **Repair summaries** to generate a fresh candidate at the remaining work. A longer approved correction may require further preparation. Reviews reject results after intervening chat/settings edits; retries remain explicit.

Each context preset has a separate **Repair prompt**. The default asks for the smallest factual correction and exact preservation of unaffected text. Repair sends the existing summary and before/after versions of changed turn parts, source summaries and earlier memory; several edits accumulate against the last incorporated revisions. It does not use the extraction/compression prompt or add new background dependencies. Exactly unchanged output is saved automatically when the old input baseline is known and coverage is unchanged. Changed wording still opens review. Summaries whose entire consumed content is unchanged are refreshed locally without a model request. Every direct consumer of a changed summary is checked independently, even if another consumer returns unchanged. Completion and saved history distinguish manual approvals, model-checked unchanged summaries and reuse without a request. Deletions/changed coverage and unavailable historical turn text retain review. An unchanged result is the model's judgment that no correction belongs in this memory, not proof of narrative correctness.

Select a current summary span and use **Edit summary** for a manual correction. Earlier versions remain saved, and dependent summaries require repair. Text edits preserve source-revision links; editing a stale summary's wording does not mark its old sources current. If every covered source turn was deleted, repair proposes removal of that coverage without a model call and still requires review. Entirely blank but still-present batches are not silently removed; unusable/non-shrinking results stop preparation.

**Prepare chat** also restores detail after a tokenizer correction, increased budget, shorter prompt or deletion. Save settings first. It remains available when current input already fits. The local pass starts from detailed history, reuses fixed oldest turn batches, then applies the usual pressure ranking to eligible saved parents. Recent history regains detail first, with older ranges kept at least as compact as newer ones. Direct manual corrections remain represented at their own spans; generated parents can expand into corrected children, and earlier-context dependencies do not pin later history. Manually edited summary boxes have an amber accent and label. Prepare restores a valid minimum completed tail even after settings changes; pending input does not count toward that minimum. A direct correction conflicting with the requested tail produces a specific range/minimum error without changing memory. If saved memory fits, no model request is made. If matching saved groups are missing but the current selection fits, it is retained without generating summaries just to rearrange it. Otherwise preparation reuses each exact valid saved batch/parent before generating a missing summary. A summarization Connection is needed only for actual model requests. Review stale memory and resolve pending repair candidates first. All summary versions and original turns stay saved. The result reports reused/new summary counts, verbatim turns and complete input; history includes initial/final reselections and every intervening reused/generated step. A final local pass incorporates newly available summaries before completing the manual action. Repeating preparation against unchanged inputs keeps the same selection without duplicate generation. Earlier Refresh history remains inspectable; its separate button has been removed.

Automatic preparation before a response and **Save next summary** also reuse exact fresh saved replacements, but preserve the committed representation and do not expand history to consume spare space. Subsequent responses recheck their complete input, including pending text. Summary quality remains unverified; reuse checks source/dependency freshness, coverage and useful measured savings.

Changed summary edits preserve old versions and source links. An identical save does nothing. Retained corrections are protected even outside the selected tree; saving one does not automatically put it in model input or make stale memory current. Use **Prepare chat** to select a fresh compatible correction. Use **Repair summaries** for stale or conflicting corrections, review the supplied editorial text, then Prepare if the repaired container remains retained. Ordinary preparation cannot sidestep this review by generating another identity for the range. Corrections may be represented through higher summaries under the same compaction rules.

Overlapping summary identities have separate timeline lanes. The summary open in inspection is outlined on the timeline. **Inspect saved summary** lists their ranges and states, and **Summary version** exposes approved version history. Inspection shows estimated summary text tokens using the shared reference counter, alongside selected versus retained status, freshness, manual corrections and whether editorial work is represented or awaiting reconciliation. Old versions are read-only.

**Clear memory** explicitly deletes every summary layer, old version, review candidate and preparation record for this chat. Original turns return to verbatim; the selected preset and saved roleplay requests remain unchanged. Return archived turns to verbatim using Prepare chat when they fit, or clear memory, before disabling context management. Changing a preset or raising a budget preserves existing selections; new settings govern future steps. Increasing the protected tail, or deleting recent turns, can require explicit Prepare chat, adjustment, or clearing memory if the old cutoff no longer satisfies the tail floor. There is no automatic partial detail-restoration policy, branch support or proactive processing after responses.

The Story sidebar shows **Total turns**, **Active turns** (saved turns kept verbatim), the input target and the current assembled input estimate. Expand **Context** for a color-coded allocation and **Prompt peek**, showing resolved messages in model order with all message bodies initially collapsed. Estimates include unsent composer text; partial assistant output is excluded. Overflow bars turn red, and near-limit bars turn blue. **Request inspector** defaults to current input and immediately reflects saved setup changes. Choose a saved attempt to inspect its exact historical request and ceiling. Endpoint and request JSON are collapsed under **Endpoint and request body**.

Budget panels retain their last result while a fresh count loads, including during memory-setting changes and preparation. Chat counting waits for one second without typing before requesting an updated preview; an explicit Preview click updates immediately. Delayed superseded responses are ignored. The server-unavailable warning clears automatically on reconnection; initial connection failures retry while the warning remains visible.

Typing `--` in the chat composer or while editing a turn input/response automatically inserts an em dash (`—`). Existing and pasted text stays literal.

Chat drafts save locally in this browser as you type, separately for each chat. They return after menus, chat switches, reloads or reopening the browser. Send keeps the text until the server acknowledges it; a failed send survives reload and can be retried explicitly after recovery. A lost acknowledgement reuses the same request identity to avoid submitting a duplicate turn. Drafts do not sync between devices or browser origins, and clearing browser data or ending a private session can remove them. If storage fails, the composer warns you to keep the page open and copy your text.

The chat composer places **Send** beside the textbox on wide screens and below it on narrow screens. The textbox starts at the Send button’s height and grows or shrinks automatically with its content; long drafts scroll within the height cap. Resizing keeps the visible turn and the reading position within it stable; **Latest turn** jumps immediately to the end. Opening or typing in a turn editor keeps the latest turn visible when already at the end, while an earlier reading position stays put. Generation progress appears inside its turn. When the endpoint returns reasoning text, a compact preview above the waiting label shows its latest lines fading upward. The preview disappears when reply text starts arriving or the attempt ends, including cancellation or failure. Use **Show reasoning** in the turn’s control row to open the full live stream; scroll up to read earlier text and use **Latest reasoning** to follow again. Reasoning is saved separately for each generation attempt and follows the selected response version. It is never sent as history or used as a summary source in subsequent requests. Old responses and endpoints without readable reasoning have no preview. Migration **12** preserves existing data and adds empty reasoning storage for old attempts. The **Summary layers** timeline keeps layer labels beside the plot, doubles zoom spacing to 40 pixels per turn, hides summary labels that do not fit and shows immediate hover/focus hints. When individual turn cells would be narrower than 5 pixels, contiguous archived and verbatim ranges become proportional grey and green bands.

Completed generated turns show endpoint-reported input/output tokens beside the turn number. Imported turns and greetings have no generation usage; older or unsupported endpoint responses show usage as unavailable. Counts describe the original request/response before later edits and may include reasoning in the endpoint’s output count.

## Model protocol and budgets

The initial adapter implements text-only **OpenAI-compatible Chat Completions**, posting to `<API base URL>/chat/completions` with `model`, `messages`, `stream: true`, `max_tokens`, and (by default) `stream_options: { "include_usage": true }`. Disable **Request token usage from the endpoint** in a Connection if it rejects this streaming option. The adapter reads `prompt_tokens`, `completion_tokens` and `total_tokens` from usage metadata, including a final empty-choice chunk; absent or invalid usage does not fail an otherwise valid response. This follows the [official streaming usage format](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events). It expects `text/event-stream` events with `choices[0].delta.content`, a `stop` or `length` finish reason, and `[DONE]`. Roleplay retains its existing `length` acceptance; summaries require `stop` to avoid accepting truncated memory. Explicit refusal metadata and `content_filter` outcomes fail safely. Optional **Fetch model list** discovery reads `<API base URL>/models` using an entered or saved key and offers filtered suggestions in Model identifier. Manual model entry remains available when discovery is unsupported. Responses API, tools, images sent to models, alternate output-limit fields, and Anthropic are not implemented. Endpoints that require a different dialect need a later adapter change.

Supported custom JSON parameters are `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`, `seed`, `stop`, and `reasoning_effort`. Unknown fields are rejected; custom parameters cannot replace messages, model, streaming, or the reserved output limit. A provider may reject a parameter it does not support. The adapter reads optional `delta.reasoning`, `delta.reasoning_content` and readable text/summary entries in `delta.reasoning_details`, using one representation per chunk and ignoring encrypted data/signatures; see [OpenRouter's reasoning format](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens). It does not inject extra settings to request reasoning or interpret inline thinking tags inside reply content. Reasoning integration is verified with synthetic streams; real-provider reasoning remains unverified. URLs cannot embed credentials, query parameters, or fragments. Credentials are sent only through the Authorization header; redirects are refused.

Prompt order follows the selected preset. Nonempty text/field markers become messages with their configured roles; Messages inserts selected verbatim parts in order. Historical summary text is inserted only at an enabled Summary marker, using its role. Blank parts are omitted while their completed turns remain in saved coverage. All resolution happens before input estimation and saved request inspection.

Input planning uses one local `cl100k_base` reference tokenizer for **all models**, plus a small shared message-framing allowance. The same measurement drives previews, prompt allocations, summary sizes/savings, compaction and summarization-window checks. New and unknown model identifiers work without mapping or downloads. No character divisor or provider-derived ratio is applied. The interface keeps its existing estimate wording; counting details and limits are retained in saved request metadata and [developer documentation](docs/TOKEN_COUNTING.md).

Estimated input must fit the chat target; estimated input plus reserved output must separately fit the Connection’s combined context window. The target is input-only, so output is not subtracted from it again. Modest differences between the reference estimate and actual endpoint tokens are acceptable around that working target. Exact remote-limit guarantees are not claimed. Overflow of the estimate fails explicitly; history is never silently dropped. Endpoint usage stays attached to its exact saved attempt; historical bodies and estimates are never rewritten. A lower estimate preserves the committed memory selection. Read-only recalculation of the reported Gemma/OpenRouter request gives 5,766 estimated input versus 5,912 reported input; see [diagnostics](docs/DIAGNOSTICS.md).

In **Libraries → Connections**, **Check connection** requests the model list using entered or saved credentials. It establishes that the endpoint accepted that request, not that every model can generate. **Send test message** immediately sends “Hi” using the current editor settings, including the configured **Reserved output tokens**, with a 30-second timeout; endpoint charges may apply. There is no separate test output cap. Successful checks and completed tests show green status text. The result shows reported token usage (or unavailable), with the test request, response and planning metadata available in the collapsed details. Neither action saves settings, adds chat turns or request history, infers a tokenizer from usage, or calibrates other requests. Empty or incomplete test responses report that nothing was saved and direct the user to send the test again. Edited endpoint URLs require entering a key again rather than forwarding a different endpoint's saved credential.

## Storage and recovery

SQLite uses WAL, foreign keys, versioned SQL migrations, and short transactions. Turns and their parts have stable identities and separate part revisions. Every mutation checks the chat revision; edits and setup changes are blocked while a response or preparation runs. Only one turn per chat can be pending, and only one generation/preparation workflow per chat can be active. Different chats may run independently. Summaries, dependencies, selected revisions and the cutoff are durable; each valid replacement and its selection commit together. The database records process ownership so a second local server cannot mark a live operation interrupted.

Each generation saves its resolved body and source coverage before calling the model. Saved records describe historical requests even after later edits. Deleting a whole turn also deletes its associated generation records. The browser subscribes to change notifications and retrieves current saved state on connection/reconnection; SSE events are not treated as a durable token log.

Preparation separately saves each credential-free summary request and step outcome. Generated repair candidates are retained but unselected until approved; approval checks the captured chat/configuration revision. A process crash preserves committed summaries, marks running preparation and unfinished steps interrupted on restart, and requires an explicit resume. Review candidates survive a restart. No model stream is claimed to be resumable. The initial viewer lists the latest 20 jobs per chat; older records remain stored and available by operation identity until memory is explicitly cleared. Automatic retention/pruning remains future work.

Partial output is checkpointed on incoming chunks at most once per 250 ms, plus explicit cancellation and graceful shutdown. A hard crash may lose output received since the last checkpoint. On restart, running operations become interrupted; no new model request is made until an explicit retry. The provider stream itself does not resume. A transport timeout, malformed/truncated stream, unsupported completion outcome, or empty first response leaves the turn pending; the same failures during regeneration keep the completed selected response.

The database file is owner-readable/writable and a newly created data directory is private. The owner password is salted and hashed with scrypt; sessions are random, stored as hashes, and expire after seven days. Saved API keys currently reside in the local database in plaintext, protected by filesystem permissions. They are excluded from public responses, previews and application logs. OS keychain integration/encryption and a password-reset flow are not yet implemented. Do not publish or casually copy the data directory.

Use **Settings → Data backup → Save backup** for a consistent SQLite snapshot, including pictures and saved API keys. Keep it private. **Inspect & import backup** under **Import backup** opens a paginated tree before any import. Review additions/overlaps, then explicitly confirm overwrites; overlapping chats are replaced as complete stories, retaining unrelated content. Cancel changes nothing. **Wipe application data** retains the owner login, this session and factory presets, revokes other sessions, and clears saved content atomically.

Backups support ORE schemas 12 and 13, up to 128 MiB and 100,000 portable rows in the input/combined result. Browser-local drafts are outside the backup. Another tab's stale edits cannot save after import/wipe; copy editor text before reloading, and review recovered composer drafts with **Use recovered draft**. An uncertain import/wipe offers an exact-command retry, including after reload/restart. See [backup format, bounds and recovery](docs/BACKUPS.md). Copying only an active WAL database's main file is not a dependable backup.

## Phone access

The default server listens on loopback only. Plain HTTP LAN binding is refused. Create the owner account locally first, then provide a certificate and key trusted by your Mac and phone, covering the hostname or LAN address you will use:

```sh
ROLEPLAY_HOST=0.0.0.0 \
ROLEPLAY_TLS_CERT=/absolute/path/to/certificate.pem \
ROLEPLAY_TLS_KEY=/absolute/path/to/private-key.pem \
"$HOME/ORE/start.command"
```

The server then prints available LAN addresses. Use an address covered by the certificate and allow access through the Mac's firewall if required. Login sessions use Secure cookies with HTTPS. Certificate provisioning and trust installation have not been selected or tested on the actual phone; routine phone use remains pending that setup. No certificate or trust settings are installed by this project.

Optional environment settings: `ROLEPLAY_PORT` (default 3000), `ROLEPLAY_HOST` (default 127.0.0.1), `ROLEPLAY_DATABASE` (default `data/roleplay.sqlite`), and the paired TLS certificate/key paths above. Source-development commands run from this project directory. Built startup resolves UI/migrations/package metadata from its installation, independently of the invoking directory. Relative explicit database overrides resolve from the invoking directory; prefer absolute paths.
